# webserv理解用 README（Pythonで学ぶ）

このREADMEは、**42の webserv を「解く」のではなく「理解する」ため**のロードマップです。

* 実装言語：**Python（理解優先）**
* 目的：**Webサーバーの中身・考え方・設計を体で理解する**
* ゴール：C++でのwebserv実装に戻ったとき、

  * 何を作っているのか分かる
  * どこが難所か分かる
  * testerが何をしているか分かる

ブラウザや環境を変えても、**このREADMEのStepを上から辿れば再開できる**構成にしています。

---

## 全体ゴール（最終的に目指す姿）

```
[Browser / curl / tester]
        |
      HTTP（文字）
        |
   [自作Webサーバー]
        |
  ┌──────────────┐
  │ Event Loop   │  ← 同時接続をさばく心臓
  └──────────────┘
   |      |      |
 request  logic  response
```

* Webは「魔法」ではなく**文字のやりとり**
* Webサーバーは「待って・読んで・判断して・返す」だけ

---

## 実装の進め方（超重要な考え方）

* ❌ 最初から完成形を目指さない
* ⭕ **動く → 理解する → 拡張する**

各Stepは「動く最小単位」になっています。

---

# STEP 0：Webサーバーの最小形

## やること

* ポートを開く
* 1接続だけ受ける
* **固定のHTTPレスポンスを返す**

## 理解すべきこと

* Webサーバーは「常駐プログラム」
* HTTPはただの文字列
* `accept → recv → send` の流れ

## このStepで得られる理解

* 「Webが動いた！」という感覚
* curl / nc で叩く意味

---

# STEP 1：HTTPリクエストを読む

## やること

* クライアントから送られてきた文字列を表示する
* HTTPリクエストの構造を知る

```
GET / HTTP/1.1
Host: localhost

```

## 理解すべきこと

* リクエストは

  * リクエストライン
  * ヘッダ
  * 空行
  * Body（ある場合）

## このStepで得られる理解

* HTTP仕様を「読むもの」として理解できる
* testerが投げてくる異常リクエストの意味が分かる

---

# STEP 2：HTTPレスポンスを正しく返す

## やること

* Status Line / Header / Body を分けて返す
* Content-Length を正しく付ける

## 理解すべきこと

* 改行は `\r\n`
* ブラウザは厳密
* HTTPはフォーマットゲー

## このStepで得られる理解

* 「ブラウザが表示されない理由」が分かる
* testerが厳しい理由が分かる

---

# STEP 3：複数接続の問題に気づく

## やること

* 2回 curl すると止まる現象を観察する

## 理解すべきこと

* 今の実装は「1人ずつ」しか対応できない
* accept / recv はブロッキングする

## このStepで得られる理解

* なぜ webserv でイベントループが必要なのか

---

# STEP 4：イベントループを作る（簡易）

## やること

* select を使って複数ソケットを監視
* 1つずつ少しずつ処理する

## 理解すべきこと

* 「待たない」設計
* Node.jsと同じ発想

## このStepで得られる理解

* 同時接続の正体
* なぜマルチスレッド禁止なのか

---

# STEP 5：静的ファイルを返す

## やること

* URLに対応するファイルを読む
* HTMLを返す

## 理解すべきこと

* URL → ファイルパス
* セキュリティ（`../`）

## このStepで得られる理解

* 「Webページを配信する」の正体

---

# STEP 6：エラー処理

## やること

* 404 / 400 / 500 を返す

## 理解すべきこと

* エラーは「失敗」ではなく「正常なレスポンス」

## このStepで得られる理解

* testerがエラーを殴ってくる理由

request → env

## 最終的に完成するファイル構成（理解用）

このREADMEのStepをすべて進めると、**最終的にこんな構成になる**のが理想です。

Python版は「構造を理解するため」のものなので、**C++版にそのまま写せる形**を意識しています。

```
webserv_python/
├─ README.md                # ← このロードマップ（いつでも戻る場所）
│
├─ main.py                  # エントリーポイント（起動・初期化）
│
├─ server/
│  ├─ server.py             # サーバー全体の管理（socket / accept）
│  ├─ event_loop.py         # selectベースのイベントループ
│  └─ connection.py         # 1接続ごとの状態管理
│
├─ http/
│  ├─ request.py            # HTTPリクエスト解析
│  ├─ response.py           # HTTPレスポンス生成
│  └─ status.py             # ステータスコード定義
│
├─ handler/
│  ├─ router.py             # URL・methodの振り分け
│  ├─ static_handler.py     # 静的ファイル配信
│  └─ error_handler.py      # 404 / 400 / 500 など
│
├─ cgi/
│  ├─ cgi_runner.py         # CGI実行ロジック（概念理解用）
│  └─ env_builder.py        # CGI用環境変数生成
│
├─ config/
│  ├─ config.py             # 設定ファイル読み込み
│  └─ default.conf          # サンプル設定（nginx風）
│
├─ www/
│  ├─ index.html            # テスト用HTML
│  └─ error.html            # エラーページ
│
└─ tests/
   ├─ manual.md             # curl / nc テスト手順
   └─ notes.md              # 気づいたことメモ
```

---

## この構成で大事な考え方

### ① main.py は薄く

* main.py は「起動するだけ」
* ロジックを書かない

👉 **C++の main.cpp と同じ役割**

---

### ② connection = 状態

* リクエストは一気に来ない
* 途中状態を持つ必要がある

👉 webserv最大の難所

---

### ③ http/ は純粋ロジック

* socketを知らない
* ファイルも知らない

👉 テストしやすい / C++に写しやすい

---

### ④ handler は if地獄を隔離

* GET / POST / DELETE
* 静的 or CGI or error

👉 「判断」を一箇所に集める

---

### ⑤ config は最後でいい

* 最初はハードコードでOK
* 構造が固まってから読む

---

* testerが何を殴っているか分かる
* C++で「書き直す」だけになる
